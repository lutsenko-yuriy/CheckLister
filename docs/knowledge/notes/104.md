# 104: Investigate Android equivalents for checklist-persistence-restart and run-gesture flows

## Notes

### 2026-09-27 — Research-WU: predictive-back gesture vs KEYCODE_BACK on Android

**Topic:** whether Android's predictive-back edge-swipe gesture and a `KEYCODE_BACK`
press are distinct dispatch paths at `targetSdk 36`, and whether
`@react-navigation/native-stack`/`react-native-screens` implements any
interactive swipe-back gesture on Android — this decides whether Half B
(`run-gesture-ios.yaml`'s Android equivalent) has anything left to cover
before spending device time on it.

**Scoping map (no verdict — topic mode, single search pass):**

| # | Source | Type | Fetch status |
|---|---|---|---|
| 1 | [Android Developers: predictive back gesture](https://developer.android.com/guide/navigation/custom-back/predictive-back-gesture) | Official docs | Fetched & verified |
| 2 | [react-native-screens Discussion #2540](https://github.com/software-mansion/react-native-screens/discussions/2540) | Maintainer discussion | Fetched & verified |
| 3 | [React Native 0.81 blog](https://reactnative.dev/blog/2025/08/12/react-native-0.81) | Official RN blog | Fetched & verified |
| 4 | [react-navigation #6893](https://github.com/react-navigation/react-navigation/issues/6893) | GitHub issue | Snippet only |
| 5 | [facebook/react-native #34529](https://github.com/facebook/react-native/issues/34529) | GitHub issue | Snippet only |

**Findings:**

- **System level (SQ1 — well confirmed):** Predictive-back edge-swipe and `KEYCODE_BACK` are
  genuinely separate dispatch paths at the platform level. Official docs (source 1): once
  an app's `OnBackInvokedCallback` is active (default at `targetSdk 33+`, default-on at
  `targetSdk 36` per source 3), intercepting back navigation via `KEYCODE_BACK`/`onBackPressed()`
  is "no longer supported" — `android:enableOnBackInvokedCallback` is the system's switch
  between the two paths.
- **App/library level (SQ2 — reasonably confirmed, one leg unverified):** `react-native-screens`
  does not implement predictive-back or any native interactive swipe-back gesture on Android
  (source 2, maintainer statement, July 2025) — a full implementation is considered unlikely
  for the current major version due to `FragmentManager` back-stack constraints. Consistent
  with source 4 (native-stack's `gestureEnabled` swipe-to-pop working on iOS only, not
  Android) — that issue's full thread wasn't re-fetched this pass, so treat as
  probably-still-representative, not independently re-verified today.
- **Net implication for CheL-104 Half B:** the two paths don't collapse at the platform level,
  but since `react-native-screens` doesn't hook either one with custom gesture code on Android,
  the app only ever consumes the *result* through `BackHandler`/`beforeRemove` — and source 3
  states "The `BackHandler` API should continue to work as before for most use cases" under
  predictive back. This suggests a Maestro edge-swipe that reaches Android's system predictive-back
  region, if it triggers navigation at all, likely fires the same app-level back callback that
  `run-exit-system-back-android.yaml` already exercises via `KEYCODE_BACK` — no distinct app
  behavior expected, which would support concluding Half B with **no new flow**. This is a
  research-level implication, not a device-verified conclusion — the Checklist-WU device probe
  (edge swipe vs `back` key, same dialog/Cancel-Discard behavior or not) is what actually settles it.
- **Gaps:** no 2026 update to `react-native-screens` predictive-back support was found beyond
  the July 2025 discussion — worth a quick re-check if screens has shipped something newer by
  the time the Checklist-WU runs.

### 2026-09-28 — Checklist-WU: device investigation (Half A + Half B)

Device: `Pixel_5_API36` emulator (`emulator-5554`, Google APIs, gesture-navigation mode
confirmed via `navigation_mode=2`), single-device, no sharding. iOS side: iPhone 17 Pro
simulator. Release build already installed matching current `HEAD` (`418e85a`) on both — no
`src/`/native changes since the last install, so no rebuild was needed.

**Half A — `checklist-persistence-restart-ios.yaml` on Android**

Reproduced the original failure standalone (tagging the flow `android` locally, uncommitted).
The failing command was index 29/30 — **the pre-restart assertion pair**, before any
`relaunchApp` had run. This immediately eliminates **H2** (persist-vs-force-stop race): the
order was already wrong before the app was ever restarted, so there is no race with `stopApp`
to investigate. The failure screenshot showed the edited item's text correct
("Scenario first edited") but its position unchanged (still row 1, not dragged to row 3) —
text edit succeeded, drag never visibly activated. This also rules out **H4** (text not
edited) directly.

**H3 ruled out:** the screen hierarchy captured at the failure point shows
`drag-handle-Scenario first edited` at bounds `[66,813]-[92,877]` — `7%,35%` of the
`1080`-wide, ~`2340`-tall screen lands exactly inside that box. The swipe's start coordinate
is correct; this is not a selector/bounds divergence.

**H1 confirmed, but incompletely resolved by duration alone.** Raising the swipe
`duration: 4000 -> 8000` (matching CheL-105 WU2's fix for the identical
`activateAfterLongPress(200)` race in `checklist-drag-reorder-ios.yaml`) and probing 10x
standalone on each platform:

| Duration | iOS (iPhone 17 Pro) | Android (`Pixel_5_API36`) |
|---|---|---|
| 8000ms | **10/10 pass** | 5/10 pass — but only 2/10 were the drag-order assertion; the other 3/10 failed earlier, at an unrelated `create-checklist`/relaunch cold-start assertion (see below) |
| 12000ms (Android only, further probe) | not re-probed | 5/10 pass — only 1/10 was the drag-order assertion; 4/10 were the same unrelated cold-start failure |

So the **drag-activation race itself** drops from ~20% (8000ms) to ~10% (12000ms) of Android
runs as duration increases — consistent with H1, and fully resolved on iOS at 8000ms
(10/10) — but is not yet at the 10/10 bar on Android at either duration tried.

**Second, independent failure mode surfaced:** 7 of the 20 Android probe runs (35%) failed
at `assertVisible: New checklist title` or a `scrollUntilVisible`/`tapOn` inside
`helpers/create-checklist.yaml` or `helpers/relaunch-and-open-checklist.yaml` — i.e. **H5**,
the pre-existing Android cold-launch/relaunch assertion-timing race already documented in
`docs/SCENARIOS.md`'s "Known flakiness" section (previously observed at ~1-in-3 *full-suite*
runs affecting 3 flows). This flow cold-launches **three times** (once via `create-checklist`,
twice via `relaunch-and-open-checklist`), exactly the "most exposed flow in the suite"
prediction the implementation plan made for H5 — and the standalone per-run rate (35%) is
much higher than the full-suite anecdote suggested, because this flow uniquely stacks three
launch/relaunch opportunities for the same race into one flow.

**Conclusion — Half A:** two separable issues, not one:
1. The iOS `4000ms -> 8000ms` duration fix is validated standalone (10/10) and ships in WU1
   regardless of the Android outcome — it was already a latent iOS flake CheL-105 WU1 had
   seen once in a sharded run.
2. Android's persistence-restart coverage is **not shippable yet**. It needs its own
   follow-up investigation, out of this ticket's scope per its own boundary ("if investigation
   surfaces a real app defect... file it as its own follow-up ticket"): (a) the drag-activation
   race needs a fix that isn't "a bigger duration constant" (duration alone plateaus around
   90% even at 12000ms — worth trying a manual long-press-then-incremental-move gesture
   sequence instead of a single synthetic `swipe`), and (b) the cold-launch/relaunch race's
   true frequency (35% per relaunch opportunity, not the "rare" impression the full-suite
   anecdote gave) deserves its own look, since three other Android flows share the same
   `relaunch-and-open-checklist.yaml` helper and are equally exposed.
   `checklist-persistence-restart-android.yaml` is **not created** by this ticket.

**Half B — `run-gesture-ios.yaml` navigation on Android**

AVD confirmed in **gesture-navigation mode** (`navigation_mode=2`), so the probe's
conclusion is valid for that mode specifically (3-button mode not probed).

- Probe 1 (edge swipe `0%,50% -> 90%,50%` on `ChecklistDetail`, no active run): **navigated
  back to Home.** The edge swipe does reach Android's system back-gesture region and does
  trigger navigation — confirming the Research-WU's prediction that Android's predictive-back
  path is live here, contrary to a naive assumption that Maestro's synthetic swipe wouldn't
  reach it.
- Probe 2 (same edge swipe during an active run, one item checked): produced the exact same
  `usePreventRemove` **"Are you sure? / CANCEL / DISCARD"** dialog, byte-for-byte the same
  copy `run-exit-system-back-android.yaml`'s `back`-key path already asserts.

**Conclusion — Half B: no new flow.** The edge-swipe gesture and the hardware/system `back`
key produce identical, already-covered app behavior (`run-exit-system-back-android.yaml`).
This matches the Research-WU's implication exactly: both paths reach the same
`BackHandler`/`beforeRemove` app-level callback, so there is nothing platform-gesture-specific
left for a `run-gesture-android.yaml` to cover. This is a deliberate, evidence-backed
conclusion, not an oversight — recorded here and in `docs/SCENARIOS.md`.

**Net effect on the plan's WU structure:** WU2 (contingent, Half B) is dropped, as expected —
the plan's own default-outcome case. WU1 ships only the iOS `4000ms -> 8000ms` duration fix
and this documentation; it does **not** add `checklist-persistence-restart-android.yaml`, since
Half A did not reach the required 10/10 bar and surfaced two issues outside this ticket's
scope. A new follow-up ticket should be filed for the Android drag-activation race and the
underestimated cold-launch/relaunch race frequency before Android persistence-restart coverage
can be attempted again.
