# CheL-74: Research: structured representation for deep-link contracts

## Notes

### 2026-09-24
- No dedicated "OpenAPI for deep links" standard exists. Surveyed: OpenAPI itself, AsyncAPI, RFC 6570 URI Templates, Android App Links (`assetlinks.json`) / iOS Universal Links (`apple-app-site-association`), Branch.io/Firebase Dynamic Links docs. Closest existing building blocks:
  - **OpenAPI's `callbacks` object** (present since OAS 3.0) is structurally the right shape for "caller provides a URL, the callee later calls back to it with its own request schema" — a runtime expression like `{$request.query.callbackUrl}` resolves to the value of our own `callbackUrl` query param, and the callback's own Path Item Object describes the result payload. This is *exactly* CheckLister's `checklister://run`/`select` shape.
  - **RFC 6570 URI Templates** are scheme-agnostic (not HTTP-specific) and are the standard way to express the request URL's shape declaratively, e.g. `checklister://run{?checklistId,callbackUrl}`.
  - **JSON Schema** (embedded as OpenAPI `parameters[].schema`) covers per-field type/format/required-ness (e.g. `checklistId` non-empty string, `status` enum).
  - Android App Links / iOS Universal Links tooling (`assetlinks.json`, AASA) solve a *different* problem — domain ownership verification for `https://` deep links — not the request/response payload schema. Worth calling out explicitly since these are the first things most people find when searching "deep link schema" and they don't actually answer this ticket's question.
  - Caveat: OpenAPI tooling (Swagger UI, most codegen) assumes `servers[].url` is `http(s)://`. The spec text doesn't strictly forbid a custom scheme, but ecosystem tooling (rendering, validation, codegen) is not guaranteed to handle `checklister://` as a server URL gracefully — this is the main practical risk of reusing OpenAPI wholesale rather than a lighter custom format.
- Concrete case (CheckLister's own contracts, read from `src/shared/links/externalLinkUrls.ts`, `src/features/runs/domain/externalRunLinks.ts`, `src/features/checklists/domain/externalSelectLinks.ts`):
  - Both verbs: scheme `checklister:`, host = verb name (`run` | `select`), empty/`/` path, request payload in query params, response delivered by GETting back a caller-supplied `callbackUrl` with the result appended as query params (discriminated by a `status` field), not returned in-process.
  - `run`: request `{checklistId: string (non-empty), callbackUrl: string (absolute, non-`checklister:`, hostname required, blocklisted schemes rejected)}` → callback `{status: 'completed'|'cancelled'|'error', checklistId: string, runId?: string (only when completed)}`.
  - `select`: request `{callbackUrl: string (same validation)}` → callback `{status: 'selected'|'cancelled'|'error', checklistId?: string, checklistName?: string (only when selected)}`.

## Debrief summary

### 2026-09-24

**What went well**
- The research answered both questions cleanly and concluded in a clear "no build needed" outcome — no dedicated deep-link-schema standard exists, but OpenAPI's `callbacks` object + RFC 6570 URI Templates + JSON Schema cover the shape well enough that no new tooling or format needs to be invented for CheckLister's own contracts.
- Findings stay in this notes file only — no ADR, no example artifact — since the ticket's actual scope was research, and the cross-project standardization decision belongs to the YAB framework repo, not this one.

**What was hard or surprising**
- Nothing.

**What to change**
- Nothing — no workflow or skill changes from this ticket.
