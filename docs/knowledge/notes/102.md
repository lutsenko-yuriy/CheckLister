# 102: Research: speed up the Maestro iOS scenario suite (8.5min full run)

## Notes

### 2026-09-27

**Framework survey (Maestro vs Detox vs Appium vs XCUITest/Espresso) — topic-mode research, evidence table + scoping synthesis**

Solidly established:
- Maestro's synchronization model is black-box polling of the UI hierarchy via UiAutomator/accessibility services, with built-in retry/timeout ([Doist Engineering, Nov 2025](https://www.doist.dev/orchestrating-ui-tests-with-maestro/), fetched; corroborated by vendor docs).
- Detox's model is gray-box: hooks into RN's JS thread, native main-thread queue, network activity, and animations to detect true app idleness, rather than polling ([Detox official "How Detox Works"](https://wix.github.io/Detox/docs/articles/how-detox-works/), fetched). Setup cost is real: native code integration into the app build, a Jest-based runner, a WebSocket mediator server.
- Maestro has official `--shard-all`/`--shard-split` CLI flags ([official CLI docs](https://docs.maestro.dev/maestro-cli/maestro-cli-commands-and-options), fetched). Documented example: 9 tests over 3 devices → each device runs 3, finishing in roughly a third of the time.

Thin or unverifiable — flagged, not usable as evidence:
- Every numeric "Detox is Xs faster than Maestro" or "Appium is Xs slower" claim traces to unsourced marketing content, including on Maestro's own site ([maestro.dev "Detox vs. Maestro"](https://maestro.dev/insights/detox-vs-maestro-reducing-flakiness-react-native), fetched — no methodology, unverifiable quotes). Near-identical number ranges ("8-12s") recur verbatim across unrelated SEO domains, a strong signal of templated/AI-generated content.
- The one source that looked like a genuine on-topic migration case study ([Jupiter engineering blog](https://life.jupiter.money/choosing-between-maestro-and-detox-on-jupiter-qa-automation-7b94e6f8759d): "Maestro ~50% slower than Detox initially, narrowed to ±10% after optimizing one slow step via a native helper") could not be fetched (403-blocked) — reported only as an unverified search-snippet claim.
- No source benchmarks Appium against Maestro/Detox with real numbers.
- No source isolates sharding's speedup from other confounding changes — the closest real number ([Eneco case study](https://maestro.dev/blog/maestro-case-study-eneco), fetched: 16h→1h) is confounded with a manual-QA→automation transition, not sharding alone.

**Implication for CheL-102:** the best-evidenced lever is Maestro's own built-in sharding (`--shard-all`/`--shard-split`) — official, no framework migration, and its documented example maps directly onto our situation (multiple local simulators/emulators already available). Switching to Detox has real architectural rationale (genuine gray-box idle-detection vs. polling) but zero trustworthy speed evidence, against a certain, large rewrite cost (native integration + Jest runner + rewriting ~14 existing flows) — weigh this against `docs/SCENARIOS.md`'s original CheL-26 rationale for choosing Maestro over Detox.

Full evidence table (all sources, fetch-verification status) is in this ticket's research subagent transcript; summarized above rather than duplicated in full.

**Empirical sharding test (this session, iOS, iPhone 17 + iPhone 17 Pro simulators, same build/environment for both runs):**
- Solo baseline (`maestro test --udid <one>`): 13/13 passed, **9m 33s (573s)**.
- Sharded (`maestro test --udid <two, comma-separated> --shard-split=2`): 13/13 passed, **5m 12s (312s)** — the max of the two shards (7 flows/5m12s and 6 flows/3m7s).
- **45% wall-time reduction** from a single CLI flag, zero flow-file changes, using devices already available locally. The split was flow-*count*-even, not duration-aware, so shard 1 (7 flows, including two of the slower ones) was the bottleneck — a duration-aware split would likely close most of the gap to the theoretical ~2x.
- This directly fills the gap the framework survey flagged: no public source isolated sharding's speedup from confounding factors (the closest, Eneco's 16h→1h, was confounded with a manual→automated transition). This measurement is a clean, controlled A/B.

**Empirical `setClipboard`+`pasteText` vs `inputText` test (this session, iOS, iPhone 17, 5 type-and-erase cycles of a ~45-character string each):**
- `inputText` (simulated keystroke typing): **40.65s**.
- `setClipboard` + `pasteText`: **41.18s** — essentially identical, marginally *slower* from the extra `setClipboard` command per cycle.
- **Negative result — ruled out as a speed lever.** Our checklist titles/item names are short strings; simulated typing isn't the bottleneck for flows like ours. Maestro's own per-command settle/poll overhead dominates regardless of input method. This contradicts my own pre-research speculation (flagged when CheL-102 was first scoped) — empirical measurement overrides it.

**Empirical swipe-duration floor test (this session, iOS, iPhone 17, `checklist-drag-reorder-ios.yaml`'s two swipes reduced from the committed 12000ms to 10000ms, in a scratch/uncommitted copy):**
- **5/5 consecutive runs passed** at 10000ms — the committed 12000ms (CheL-98) has real headroom above the actual minimum. CheL-98 already established 4000ms and 8000ms both raced the `activateAfterLongPress(200)` timer intermittently, so the true floor is somewhere in (8000, 10000].
- Did not probe further (e.g. 9000ms) — diminishing returns for a research pass, and CheL-98's own standard for this exact flow was "multiple consecutive runs" as sufficient confidence, which 5/5 meets. A tighter floor could be pinned down with more runs if the eventual time savings (a few seconds per flow) justify it.
- **Not applied to the committed file** — this is a research finding, not an implementation change; actually lowering the duration is follow-up implementation work per `docs/workflows/RESEARCH.md` ("this skill never implements anything").

**Fixed-wait audit:** `grep -rn "extendedWaitUntil\|waitToSettleTimeoutMs\|sleep\|- wait" .maestro/` returns nothing — no fixed sleeps or waits exist anywhere in the flow files. This scope item from the ticket is already satisfied by existing discipline; nothing to trim.

**"Test robot" / shared-fixture architecture — reasoned, not empirically tested (internal code precedent, no external research needed per `docs/workflows/RESEARCH.md`):** most per-flow wall time is `helpers/create-checklist.yaml`'s repeated cold app launch + checklist/item creation, run independently in every one of the ~14 flows. A shared-fixture ("robot") pattern reusing one long-lived app session/checklist across flows would cut that redundant setup — but:
- It directly conflicts with `docs/SCENARIOS.md`'s existing, deliberate isolation convention: "Each flow cold-launches without clearing storage, creates a uniquely named `Scenario <timestamp>-<random>` checklist... deletes only that checklist on success" — precisely so flows never interfere with each other's state. This is the same isolation principle CheL-34/CheL-97's snapshot mechanism exists to protect at the app-data level; sharing a fixture across flows reintroduces cross-flow interference risk at a different layer.
- Maestro's flow model has no first-class mechanism for sharing app state across separate flow files/processes beyond what CheL-34/97 already built (snapshot-and-restore) — building a "robot" layer would mean either a much bigger custom framework around Maestro, or moving to a framework with native support for this (Detox does support persistent app sessions across a describe block, one of its real architectural differences from Maestro's black-box-per-flow model) — which loops back to the framework-survey trade-off, not a free architecture change within Maestro.
- **Conclusion: subsumed by sharding.** The bottleneck this idea targets (repeated cold-launch overhead) is already addressed more cheaply by running flows in parallel across devices (measured: 45% wall-time reduction from `--shard-split=2` alone, zero flow-file changes) rather than by making individual flows themselves cheaper to set up. Recommend not pursuing a shared-fixture architecture — the cost (rearchitecting flow isolation, likely reintroducing the exact flakiness class CheL-34/97/98 fixed) outweighs a benefit sharding already captures more cheaply.
