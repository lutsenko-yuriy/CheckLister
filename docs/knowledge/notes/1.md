# 1: Checklists

## Notes

### 2026-09-16

**Organize tickets as soon as features are identified, not on a separate ask**

While filling in `docs/PRODUCT_SPEC.md`, all 5 v1 features were fully
clarified through dialog in the same session. The user then had to
separately ask "organize features into tickets" as a follow-up step. Once a
feature is unambiguous and coherent (the same bar the `brief` skill's step 3
already uses to decide whether to proceed to ticket creation), there's no
reason to wait for an explicit "make tickets" request — go ahead and create
the tickets right away as part of identifying the features, rather than
treating spec-writing and ticket-organizing as two separately-triggered
steps.

### 2026-09-16

**Fix review-round findings immediately when it makes sense, rather than waiting to be asked**

After the `review` and `audit` skills posted their findings on PR #6 (one
architectural drift, two runtime races/error-handling gaps), the user asked
to fix them right away. `docs/workflows/FEATURE.md` step 10.2 already allows
this ("either fix it in a new commit and push, or post a one-sentence
explanation of why the fix will not be implemented") — the default response
to a review finding should be to just fix it in the moment when the fix is
straightforward and low-risk, not to wait for an explicit "go ahead" each
time. Reserve the "explain why not" path for findings that are genuinely
disputable, out of scope, or need a design decision only the user can make.

## Debrief summary

### 2026-09-17

**What went well**
- End-to-end delivery: a real, working feature (create/rename/delete
  checklists, navigation to a detail screen) shipped from a cold repo in one
  session, verified on both iOS and Android.

**What was hard or surprising**
- The stack itself was new territory — user was only just getting familiar
  with React Native going in.

**What to change**
- Should have run the `plan` gate before implementing. The ticket clearly
  matched its criteria (new domain entities, new dependencies, multiple
  files/layers), but it got skipped because the user asked to jump straight
  to implementation, and that request was treated as blanket permission to
  skip every pre-implementation gate rather than just the ones it clearly
  meant. `docs/workflows/FEATURE.md` step 1.3 now says to confirm once
  before skipping the plan gate specifically in that situation.
