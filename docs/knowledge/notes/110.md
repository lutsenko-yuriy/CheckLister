# CheL-110: Android drag-activation race and cold-launch/relaunch race frequency: investigate root cause

## Notes

- 2026-09-28: Tested the "manual long-press-then-incremental-move" hypothesis for the Android drag-activation race. Maestro's `swipe` command has no hold-before-move primitive (only linear start→end→duration interpolation, confirmed via docs.maestro.dev). The only alternative available without raw touch-event injection is `adb shell input draganddrop`, Android's own drag primitive — tested it directly against the emulator as a standalone probe (bypassing Maestro) at several durations on the same drag-handle coordinates `checklist-drag-reorder-ios.yaml` uses. Results: 0/10 pass at 300ms (same no-op failure mode as a too-fast swipe), and at both 2000ms and 8000ms it sometimes produced a new failure mode not previously documented — a partial/adjacent-item swap (drag stops at the neighboring slot) instead of either a clean full reorder or a clean no-op. It only succeeds reliably at large durations (8000ms+), matching swipe's own known curve. Conclusion: draganddrop is not a mechanically distinct primitive from swipe for RN's JS-side gesture handling — both are linear pointer interpolations at the OS level, and neither can express a true "hold still past the 200ms threshold, then move" sequence. Testing that would require raw touch-event injection (e.g. sendevent), which neither Maestro nor adb's `input` command expose. This rules out the ticket's proposed workaround as testable with current tooling; the remaining paths are (a) accept the ~80-90% ceiling and add retry logic around the drag step instead of chasing 10/10, or (b) investigate app-side: whether activationDistance/touch-slop config on react-native-reanimated-dnd's pan gesture can be widened for Android specifically.

- 2026-09-28: Measured the Android cold-launch/relaunch assertion-timing race directly (standalone probe, `am force-stop` + `am start` cycles against `emulator-5554`, polling `uiautomator dump` for `New checklist title`, matching `helpers/create-checklist.yaml`'s and `helpers/relaunch-and-open-checklist.yaml`'s first assertion). Two runs of 20 trials each: (1) raw `am start` to text-visible: 19/20 exceeded Maestro's 7s default `assertVisible` timeout, avg 10.09s, max 16.23s. (2) `am start -W` (blocks until first frame drawn, closer proxy for where Maestro's own `launchApp` likely hands control back) to text-visible: only 1/20 exceeded 7s, avg 5.54s, max 13.57s — but with a fat right tail (most trials cluster 4-6s, one spiked to 13.57s). Conclusion: this is a **structural timing-margin problem, not rare flakiness**. The app's cold-start-to-interactive-home-screen latency on this Android emulator sits right at or above Maestro's 7s default timeout in the typical case, with high enough variance (single-run spikes to 13-16s) that CheL-104's 35% per-launch-opportunity failure rate is fully consistent with this distribution, not an anomaly. Candidate fix (not yet applied, per this ticket's own boundary against silently bumping timeouts without quantified evidence): raise the `assertVisible: New checklist title` timeout in both shared helpers to ~20000ms — that would have covered all 40 combined samples across both probe runs. This is a helper-level fix, not an app defect; the assertions themselves are correct once the race clears.

- 2026-09-28: Applied the candidate fix and quantified the new pass rate before shipping it. `assertVisible` has no `timeout` field of its own (Maestro CLI 2.10.0 rejects it: "Unknown Property: timeout") — used `extendedWaitUntil: { visible: ..., timeout: 20000 }` instead, which is Maestro's documented mechanism for waits beyond its 7s default and doubles as the assertion. Verification: a standalone flow mirroring CheL-104's most-exposed case (`create-checklist` + 3x `relaunch-and-open-checklist`, no drag step, to isolate the cold-launch race from the separate drag-activation race) run 15x against `emulator-5554` — **15/15 passed (60/60 cold-launch opportunities)**, versus the ~35% per-launch baseline failure rate measured before the fix.

- 2026-09-29: Fixed the drag-activation-race half. Wrapped `checklist-persistence-restart-android.yaml`'s drag swipe (`duration: 8000`, matching the existing floor) plus its two order assertions in Maestro's native `retry` command (`maxRetries: 3`, the documented 0-3 range) — a failed attempt leaves either a no-op or an adjacent-slot swap, but the wrapped assertions only pass on the true final order, so a retry starting from a wrong layout still fails and retries again rather than false-passing. Added the previously-withheld `checklist-persistence-restart-android.yaml` (tagged `android`) and verified 10/10 full-flow runs on `Pixel_5_API36` (3 relaunches + retry-wrapped drag each), drag succeeding on its first attempt all 10 times, consistent with 8000ms's already-measured ~80-90% single-attempt rate. Separately validated the retry mechanism itself actually works when needed: a throwaway `duration: 2000` variant (known near-0% floor) exhausted all 4 attempts (1 + 3 retries) and failed cleanly in 5/5 stress runs, with screen-hierarchy dumps confirming the same unchanged item order across all 4 attempts each time — a clean no-op, not a compounding partial-swap, so a failed attempt doesn't corrupt state for the next retry. One false lead worth recording: an early run showed "Scenario second" rendering truncated to "Scenario" across all 4 retry attempts, alongside a stray floating IME overlay and, shortly after, a "Process system isn't responding" ANR dialog on screen — this was a degraded emulator after a long multi-ticket session, not an app bug; a clean `adb emu kill` + relaunch reproduced the identical steps with no truncation. Also self-caught a `docs/CONSTRAINTS.md` violation mid-investigation: ran an ad-hoc `adb exec-out screencap` while a Maestro flow was actively running against the same device (the exact scenario #97 documented as able to hang a run for ~1h47m) — it happened to resolve quickly this time, but the run it overlapped with was discarded as confounded rather than trusted, and no concurrent adb commands were run for the rest of the investigation.
