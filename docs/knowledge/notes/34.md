# 34: Isolate Maestro scenarios from persistent test data

## Notes

## Debrief summary

### 2026-09-26

**What went well**
- The restore-before-run (not after) design held up under real verification: seeded data survived two full suite runs byte-for-byte unchanged, confirmed by direct AsyncStorage-file inspection rather than just trusting the UI.

**What was hard or surprising**
- Three scenario flows (`run-complete.yaml`, `run-history.yaml`, `checklist-drag-reorder-ios.yaml`) failed during manual verification — root-caused to a pre-existing, unrelated first-tap-swallowed-after-text-entry issue (same class as CheL-54, different screen), not caused by this ticket's snapshot mechanism. Confirmed independent of this PR by reproducing via a bare `maestro test` invocation with no restore step involved. Filed separately as #98.
- These failures had gone unnoticed until this ticket's manual verification forced someone to actually watch the suite's output closely — the suite isn't run often enough, or its output isn't scrutinized closely enough, for this class of regression to surface promptly.

**What to change**
- Get scenario coverage running automatically and more often instead of relying on someone remembering to run it locally. macOS CI runners are expensive, so Android-on-Linux (hardware-accelerated emulator) is the cheaper path to *some* continuous coverage — filed as #100, to be scoped with its own `/plan` (emulator-runner choice, AVD/API level, build step, required-vs-informational check status). iOS CI integration remains a separate, likely costlier follow-up if ever revisited.
