## Notes

- 2026-11-07: When a new dependency is introduced, the plan should also consider its licensing and any other legal aspects (not only technical fit). Raised by the user after the plan proposed react-native-image-picker and @dr.pogodin/react-native-fs; licenses were only checked after the plan was approved.
- 2026-11-07: The plan chose @dr.pogodin/react-native-fs 2.41.0 after checking only its license and iOS/Android fit on paper. In WU1 its Android build failed on our React Native 0.87.1 (codegen: "ArrayBuffer is only supported for C++ TurboModules"; the package itself builds against RN 0.88), so the user approved switching to react-native-file-access (MIT, from the plan's alternatives). Next time, when a plan proposes a native dependency, check its supported React Native version range and build it on both platforms (a throwaway install plus a Gradle/Xcode build) before the plan is approved, not in the first implementation work unit.
- 2026-11-07: Demo mode: on opening the WU1 PR (#163) the QR code was generated by `demo.py render` but never pasted into the reply to the user; a later `render` call was piped through `head -1`, which cut the QR block, and the first-per-WU QR was lost. Raised by the user ("The QR code was not posted even though it was generated and it was the first time you published the PR"). Rule to apply: paste `render` output verbatim, never pipe or truncate it, and show it in the reply right after the PR is created.
- 2026-11-07: After swapping a native dependency, RN's `pod install` privacy-manifest aggregation only appends to `ios/CheckLister/PrivacyInfo.xcprivacy`; entries from the removed library (disk-space reasons from the old fs package) stayed behind. Restore the file from `origin/main` and re-run `pod install` after removing a pod.
- 2026-11-07: PR size. WU1 (#163, +1,013) and WU3 (#165, +1,387 across 26 files, ~550 lines of production code) went over 1,000 changed lines; the plan had flagged WU3 as over the estimate on purpose. The user approved merging #165 as is and asked that this be raised at the debrief: decide what to do about PRs over 1,000 lines (split at planning time? count tests/docs or not? a process rule in MULTI_WU.md and the plan skill?). Not decided yet.

## Debrief summary
### 2026-11-07

**What went well**
- Running the iOS scenarios before shipping.
- Running the Android scenarios on CI.
- The Android run found a real bug (Android's `mkdir` rejects an existing folder, so a run's second photo failed to save) that the unit tests and the iOS run missed.

**What was hard or surprising**
- The scenario runs were demanding, mostly in time: two native builds per WU and long flow lists.
- Flows broke on things unrelated to the feature: the new "Add photo to <item>" label matched loose `.*Item.*` taps, and the events list is longer on Android. An exact-text fix then broke iOS, where the checkbox label has extra words.
- Demo-mode QR blocks were missed at #163 and again at #166.

**What to change**
- Run tests and scenarios on CI, not locally (`FEATURE.md` step 10.0); iOS stays a local run before the final ship until CI has an iOS job.
- Cap a WU at 1,000 changed lines or get an explicit OK at plan time (`MULTI_WU.md`, `plan` skill).
- Vet every new dependency's licence, React Native range and both-platform build before plan approval (`plan` skill).
- Paste the `render` output in the reply text (`demo-mode.md`).
- Selector rules in `SCENARIOS.md`; the strict-mock code smell in `CODE_STYLE.md`; run Android in any WU that adds native file or permission code.
- Follow-ups to ticket: an iOS scenario job in CI; a notification mechanism for when the user is away, modelled on Mordovorot and Habit Loop.
